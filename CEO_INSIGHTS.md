# What This Project Tells a CEO

RoutingOpt is a small vehicle-routing optimizer, but the way it got built — and
rebuilt, three times — is more interesting than the app itself. Here's what's
worth taking upstairs.

## 1. We tested "AI-in-the-loop" and it didn't earn its keep — twice
The project started with an LLM (Gemini, then a local model) picking which
routes to throw away and re-optimize at each step of the solver. Both times,
that LLM step was eventually ripped out. Not because AI failed at the task,
but because a well-tuned classical algorithm (plus a specialized 30-year-old
C solver, LKH3, for the hard cases) was faster, cheaper, more predictable, and
just as good — for this specific kind of problem.

**Takeaway:** "Add an LLM" is not automatically the right move for every
optimization or decision-making step in a product. For well-understood,
deterministic problems, classical algorithms can quietly outperform an LLM
wrapper on cost, latency, and reliability. The right question isn't "should
we use AI here," it's "does this specific step benefit from judgment/reasoning,
or from raw search speed" — and it's worth actually testing both, the way this
project did, rather than assuming.

## 2. The infrastructure bill for this product is $0
The solver was moved to run 100% inside the user's browser (compiled to
WebAssembly, executed in a background thread) instead of on a server. There is
no backend doing the compute anymore — every user's browser pays for its own
optimization run. The app is now a static site with no server to provision,
scale, patch, or pay for.

**Takeaway:** for compute-heavy but stateless tools (calculators, optimizers,
simulators, configurators), pushing the workload client-side can turn a
per-user infrastructure cost into zero marginal cost — at the price of some
upfront engineering to get the compute portable (in this case, C/Go compiled
to WebAssembly). Worth asking on future builds: does this actually need a
server, or does it just need to look like it does?

## 3. Correctness was never negotiable, even while everything else changed
Across three different solver backends and two different LLM providers, one
thing never moved: every proposed route was checked against hard constraints
(vehicle capacity, delivery time windows) before being accepted — no matter
which component produced it, including the "smarter" LKH3 solver, which
internally treats constraints as soft penalties rather than hard rules.

**Takeaway:** the fastest way to make an optimization or AI-assisted feature
trustworthy is to separate "propose an answer" from "verify the answer is
valid," and never skip the second step regardless of how the first one was
generated. That pattern generalizes directly to anything AI-assisted the
company ships to customers — proposal and validation should be independent,
non-negotiable stages.

## 4. Speed of iteration was very high, and cheap
The project went through three full architectural pivots (cloud LLM → local
LLM → no LLM; server-hosted solver → fully client-side; dynamic backend →
static site) in about five days, with an AI coding assistant doing the
implementation work. The total API cost of that work — every prompt across
every session — was on the order of $100–150.

**Takeaway:** the cost of *trying* an architecture and then throwing it away
if it doesn't work has dropped enormously. That changes the calculus for
technical bets: it's now cheap enough to build the wrong thing on purpose,
learn from it fast, and pivot, rather than spending weeks in design review
trying to pick the right architecture up front.

## 5. The core engine is a reusable asset, not a one-off demo
Strip away the demo UI and this is a general-purpose vehicle-routing-with-
time-windows solver — the exact problem behind last-mile delivery, field
service scheduling, and fleet dispatch. The solver, the feasibility checker,
and the "give the specialist solver the hard cases" pattern are all
domain logic that would carry over directly into a production routing
product, not throwaway prototype code.

**Takeaway:** worth flagging to the team building or evaluating logistics/
routing tooling — there's a validated technical approach here (client-side
WASM solver + specialist sub-solver for hard cases) that's cheaper to run at
scale than a server-side equivalent, and it already exists.

## 6. Scaffolding tools bring their own defaults — know what you inherited
The project was originally generated by an AI app-builder (Google AI Studio),
which is why it defaulted to Gemini as its LLM provider even though the team
ended up wanting something else (local, private inference). That default
took deliberate work to unwind.

**Takeaway:** AI-generated scaffolds are a great way to get moving fast, but
they encode vendor and architecture choices the requester may not have
consciously made. Worth a checkpoint early in any AI-scaffolded project:
"what defaults did the tool pick for us, and do we actually agree with them?"
